Design system — les fuites entre les lots

La plainte « manque de cohérence » est fondée, mais elle ne vient pas des lots livrés — elle vient de ce qui est passé entre eux : ~39 couleurs de familles recopiées en dur avec des alphas incohérents, la vue Pièce manuelle construite en styles inline hors système (exactement l'écran que le client pointe), et deux fusions annoncées par la charte jamais livrées.

P0 Les familles de couleurs en dur — 39 occurrences, 6 alphas

Chaque famille sémantique (off/deff/util, tiers t0-t4) est déclinée à la main partout : bordures teintées à .5 sur les chips de stats mais .55 sur les sets et .3 sur les rulerefs ; fonds « sélectionné » à .16 ici, .14 là, badges à .12/.13/.15 selon le tier. Personne ne peut ajouter un composant teinté sans se tromper — et le mode clair doit se rappeler d'écrire sa rustine à chaque fois. Deux l'ont oublié :

Bugs de contraste light déjà présents

.s-t1 .rc-id et .ruleref.t1r : texte #8fbde4 sans surcharge light — bleu pastel sur fond crème, ≈ 2,1:1, quasi illisible. Le symptôme type du non-tokenisé.

Correctif : 3 rôles × 8 familles = 24 tokens de tints (--off-hi/-bd/-dim, --t0-hi/-bd/-dim…) posés dans :root et surchargés une fois dans body.light ; les ~39 consommateurs se réécrivent mécaniquement et les rustines light disparaissent. ~2-3 h, mécanique.

P0 Le « mix bizarre » : un 6ᵉ disclosure

L'app compte cinq coquilles repliables : details.acc, details.panel, .controls-acc, .side-acc… et .tm-step, qui a exactement la même anatomie que details.acc mais réimplémente le pliage en JS avec un chevron différent (▾ droite/180° vs › gauche/90°). Deux grammaires de chevron dans la même vue. S'y ajoutent : un bouton dans un bouton (« vider » dans le header cliquable, d'où un hack de marges commenté dans le CSS), et trois contrôles différents pour le même geste « choisir une valeur » (seg pour le slot, chips pour main et set) — avec un seg fond-panel2 posé sur un corps panel2 qui le rend invisible.

Correctif : une seule coquille disclosure (chevron › unique), le slot passe en chip.pick comme main et set, « vider » sort du header. ~2 h.

P1 Les styles inline de la Pièce manuelle

37 occurrences de style=" dans les templates JS. Légitimes : les valeurs calculées (largeur de jauge, couleur d'accent). Tout le reste est du CSS déguisé, concentré sur la vue que le client trouve incohérente : panneaux de verdict (border-left inline), lignes d'explication en 12.5/11.5 px — les tailles que l'échelle devait tuer, réintroduites par cette vue —, marges ad hoc partout.

/* Classes à créer (extrait) */
.panel.verdict.ok{border-left:3px solid var(--util)}
.panel.verdict.rej{border-left:3px solid var(--off)}
.xr{font-size:var(--fs-1);color:var(--muted)}  .xr.dim{color:var(--faint)}
.ctl.grow{flex:1 1 240px}  .cols-2{…}  .dim{color:var(--faint)}

Critère de tri : un style= qui encode une donnée est légitime ; un style= qui encode un choix de design est une classe qui n'a pas été créée.

P1 Les fusions annoncées, jamais livrées

  • .stat-card vs .cov-card : la charte disait « doublon exact — fusionner » ; les deux existent, avec paddings, labels et grilles différents ;
  • .fchip vs .chip.pill : la charte décrit une classe qui n'existe pas — soit livrer, soit amender ;
  • .mini/.p-main : badges passifs à bordure pleine = costume d'interactif (violation du principe « la bordure est une affordance »).
La charte est le contrat, pas la brochure. Un document de référence qui décrit un état qui n'existe pas produit exactement l'incohérence que le client ressent.— ingénieur design system

La règle de lecture qui verrouille tout : bordure pleine = interactif · fond teinté sans bordure = badge passif · hairline = conteneur. .ruleref vs .rc-id illustrent déjà ce contrat (même costume ± la bordure) — c'est le modèle à généraliser.

Gouvernance — les 6 règles pour toute future feature

  1. Zéro littéral de style dans un template JS — un style= n'est autorisé que pour une valeur calculée depuis une donnée. Test de revue : grep 'style="' | grep -vE 'width:|background:#' doit sortir vide ;
  2. Une couleur de famille ne s'écrit qu'une fois — tout passe par --fam-hi/-bd/-dim ; plus jamais de rustine body.light .x{color:#…} : si un light diverge, c'est le token qui a un trou ;
  3. Toute valeur passe par une échelle, tout écart se commente (modèle existant : le 16px anti-zoom iOS) ;
  4. On ne crée pas de composant, on décline — une nouvelle famille exige une ligne ajoutée à la matrice dans la même PR. La recopie guidée et le mode farm se construisent intégralement avec l'existant ;
  5. La bordure est un contrat — un passif ne reçoit jamais de bordure pleine ;
  6. Un seul disclosure, un seul chevron — les notes par règle, typiquement, sont un details.acc dans le corps de carte, rien d'autre.
