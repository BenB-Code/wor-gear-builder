UX — un seul vocabulaire, trois moments d'usage

Le produit est solide sur le fond (moteur, pédagogie, explicabilité des verdicts) mais il superpose trois vocabulaires pour les mêmes concepts et trois contextes d'usage dans les mêmes écrans — construire à tête reposée / vérifier pendant le farm / ressaisir devant le jeu. C'est cela que le client verbalise en « manque de cohérence », pas la densité.

P0 Trois widgets pour un seul état : l'onglet actif

Le « jeu de règles actif » est piloté par une rangée d'onglets (vue Règles), un <select> « Onglet » (Testeur) et un autre (Sets). L'utilisateur ne construit jamais le modèle « il y a UN jeu de règles actif, global, que toutes les vues regardent » — il croit régler un paramètre local du Testeur. C'est l'incohérence la plus structurante de l'app.

┌─ RAIL ──────────────────┐
│ ◆ Tri d'équipement      │
│ JEU DE RÈGLES ACTIF     │
│ ┌─────────────────────┐ │
│ │ End Game | Strict ▾ │ │  ← pilote Règles, Testeur, Sets
│ └─────────────────────┘ │
│ ▸ Règles            18  │
│ ▸ Testeur               │
│ ▸ Sets & transfo    48  │
│ ▸ Référence             │
│ ─────────────────────── │
│ Saisie in-game     0/18 │  ← enfin lisible : même contexte
│ ▓░░░░░░░  [► Recopier]  │
└─────────────────────────┘

Corollaire de nommage : « Onglet » (collision avec les onglets du navigateur ET la nav latérale) → « Jeu de règles » partout — le lede de la vue Règles utilise déjà ce terme pour définir le mot onglet, preuve qu'il ne se suffit pas.

P0 Le Testeur : deux intentions collées ensemble

ModeQuestion poséeContexte
Couverture« Mon ruleset est-il sain ? »bureau, avant saisie
Échantillon« Que gardera-t-il en pratique ? »bureau, avant saisie
Pièce manuelle« CE drop, je le garde ? »pendant le jeu, téléphone en main

Couverture et Échantillon sont deux facettes d'un même audit — leur cohabitation est légitime. Pièce manuelle est un outil de terrain, à cadence répétée, enfoui au 3ᵉ rang d'un sous-mode : 4-6 interactions de trop à chaque pièce. → le cas « pendant le farm » reçoit un mode plein écran dédié (voir Intégration) ; et les modes se renomment par la question, pas la méthode : « Audit complet » · « Simulation de drops » · « Vérifier une pièce ».

Parcours clés — les frictions

P0 Créer sa première règle

  • Mis en échec dès l'ouverture : « requis > liste — injouable » s'affiche alors qu'on n'a encore rien fait. Un état initial ne doit jamais être une erreur → validation « lazy » après première interaction ;
  • L'ordre du formulaire inverse le modèle mental : on demande le Nom en premier alors que le nom est la conclusion (le placeholder l'avoue : « ex. DPS scaler, Tank quad… »). → Ensemble → Sets → Main → Subs → Requis → Nom, avec suggestion auto éditable ;
  • P1 Aucun feedback de portée : le dialogue est le seul endroit où l'on écrit une règle sans voir ce qu'elle attrape, alors que le moteur existe. Une ligne vivante « ≈ 36 profils gardés (2,1 % de ses sets) » recalculée à la volée fermerait la boucle création→test dans le geste même de création — le meilleur ratio valeur/encombrement de tout l'audit ;
  • P1 grille de 30+ sets sans pré-filtre (mémoriser le dernier filtre de tier) ; « Ensemble 2 pièces » sans traduction slots dans le select.

P1 Auditer sa couverture

Points forts réels : cartes, colonne diagnostic, « c'est voulu, pas cassé ». Frictions : les alertes ne dominent pas (18 lignes « ok », l'œil balaie tout pour vérifier qu'aucune n'est en alerte → alertes triées en tête ou bandeau « ⚠ 2 règles à revoir ») ; la carte « 0 règles qui ne gardent rien » devrait être verte quand tout va bien — aujourd'hui un état parfait ressemble à un état neutre.

P0 Vérifier un drop pendant le farm

Le verdict est sous le pli — 4 panneaux d'étape occupent le premier écran, LA réponse arrive à mi-page. → verdict sticky, stepper réellement séquentiel (replier l'étape validée, ouvrir la suivante — le code prévoit le repli, tout est pré-ouvert). Et l'ordre des étapes ne suit pas la lecture d'un drop in-game : en jeu on lit slot → set → main → subs ; l'app demande le set en dernier. → Slot → Set → Main → Subs.

P0 Ressaisir en jeu

Un rituel complet (18 règles champ par champ, l'écran de jeu à côté) sans mode dédié : l'écran est optimisé pour éditer, pas pour dicter. → mode recopie guidée (voir Intégration). Garde-fou modèle : signaler « modifiée depuis la saisie » sur une règle cochée puis éditée, sinon la progression ment.

P1 Partager

Trois concepts voisins sans hiérarchie sur la même barre (Exporter = sauvegarde, Partager = transmission, clé in-game = paramètre du jeu). → un bouton « Partager ▾ » (lien / JSON / imprimer), la clé devient une propriété d'onglet repliée — elle sert une fois par ruleset et vit en permanence dans le bandeau.

P0 Le point le plus subtil : « recyclée mais subs couvertes »

Trois panneaux se suivent : verdict ferme, puis « règles qui couvrent ces subs » au conditionnel avec les mêmes ids, puis « règles proches ». Deux lectures fausses possibles : « D2 la garde… mais seulement à condition ? » (contradiction perçue) ; et pour une recyclée dont les subs matchent : « des règles la couvrent, donc je la garde ? » — non, et c'est précisément l'info la plus précieuse (bonnes subs, mauvais set — le candidat idéal pour « créer la règle depuis cette pièce »).

┌──────────────────────────────────────────────────┐
│ ✗ RECYCLÉE                                       │ ← verdict, ferme, seul
├──────────────────────────────────────────────────┤
│ Pourquoi — et à quoi elle a failli servir        │ ← UN panneau diagnostic
│ Subs excellentes pour :  D2 Support · D5 Heal HP │
│   … mais leur set requis est : Ailes de la grâce │
│   [＋ Créer une règle depuis cette pièce]        │
│ Presque gardée par :  D1 Inspiration             │
│   AS en main — attendu : ATK%                    │
└──────────────────────────────────────────────────┘

Quand la pièce est gardée, le panneau « couvrantes » disparaît à 4/4 subs — il n'a de valeur que pendant la saisie, comme prédiction (usage que le code assume déjà à 2-3 subs).

P0 Hiérarchie de la vue Règles

Ce qui devrait dominer : la liste. Ce qui domine : l'appareillage — ~40 % de la hauteur avant la première règle (un écran entier de chrome en mobile). Rework sans rien supprimer :

├ Onglets [ ][ ][ ] +        ┤      ├ Onglets [ ][ ][ ] + ⋯           ┤
├ [Renommer][Dupliquer][Sup] ┤      │  ⋯ = menu : Renommer, Dupliquer,│
├ [Exporter][Partager]       ┤      │  Supprimer, Partager ▾, Clé…    │

Les actions d'onglet sont des opérations rares → menu « ⋯ » contextuel. La liste remonte d'un écran.

Modèle mental — le lexique

  • P1 « 2 pièces vs 3 pièces », trois vocabulaires : left/right (code), « Ensemble 2/3 pièces » (Règles), « côté » (Échantillon), « arme & torse » (Sets). Le joueur pense slots. Norme : libellé principal = slots (« Arme & torse », « Bracelet · Collier · Bague »), qualificatif = « (set 2/3 pièces) ». Jamais « côté » seul ;
  • P2 généraliser le garde-fou « c'est voulu, pas cassé » : chaque métrique anxiogène (1,02 % gardés) mérite son « c'est normal » contextuel ;
  • P1 le panneau « Contraintes de main par slot » apparaît sous les trois modes du Testeur alors que c'est un réglage quasi immuable → « Paramètres du simulateur » repliés, une fois ;
  • P1 l'Échantillon rend sa réponse (« 48/2000 — 2,4 % ») en 13 px mono au milieu des contrôles → la promouvoir au même traitement que les cartes de la Couverture (cohérence inter-modes) ;
  • P2 Sets & transfo : dire explicitement que la colonne Couverture réagit au jeu de règles actif ; lien croisé Référence ↔ Échantillon (les taux qui pilotent la simu).
L'app ne manque ni de fonctions ni de place : elle manque d'un seul vocabulaire (jeu de règles, slots, verdicts) et d'une séparation nette entre les trois moments d'usage — construire, farmer, ressaisir. Les 10 features du backlog s'intègrent toutes sans un pixel de chrome permanent.— spécialiste UX
